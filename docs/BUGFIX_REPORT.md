# Bug Fix Report — Voyage Create Dialog & Achat Persistence

**Project:** BombaProMax — FourniPro (WPF) + FourniProApi (ASP.NET Core)  
**Date:** June 2025  
**Branch:** master  

---

## Overview

A series of bugs prevented the Voyage creation dialog from working end-to-end. The issues ranged from silent app crashes, WPF binding misconfiguration, a PostgreSQL data-type mismatch, and a database schema constraint overflow. All five issues have been resolved and the full voyage submission flow (including Achat) now works correctly.

---

## Bug 1 — Silent App Crash on "Add Voyage" Click

### What happened
Clicking the **Add Voyage** button in `VoyagesSection.xaml` caused the entire WPF application to immediately exit with code `0xC000041D` (fatal unhandled exception). No error dialog appeared.

### Root cause
The application had no global exception handler wired up. When an unhandled exception occurred anywhere during dialog creation, Windows terminated the process silently, with no visible message.

### Fix
- Added a `DispatcherUnhandledException` handler in `App.xaml.cs` that catches unhandled UI-thread exceptions and shows them in a `MessageBox` instead of crashing silently.
- Added a `try/catch` in `VoyagesSection.xaml.cs` around the dialog creation and `ShowDialog()` call so dialog-level failures also surface to the user.

## Bug 2 — WPF Read-Only Binding Exception (Computed Totals)

### What happened
After the global handler was added, the real error was revealed:

```
InvalidOperationException: A TwoWay or OneWayToSource binding cannot work
on the read-only property 'VenteTotal' / 'CreditTotal' / 'AchatCout'
```

This crashed the dialog immediately on open.

### Root cause
In `NouveauVoyageDialog.xaml`, `Run.Text` bindings were left at the default `Mode=TwoWay`. WPF's `Run.Text` defaults to `TwoWay`, but `VenteTotal`, `CreditTotal`, and `AchatCout` are **computed/read-only** properties on `NouveauVoyageViewModel` (they have no setter). WPF tried to push values back into them and threw.

### Fix
Added explicit `Mode=OneWay` to all `Run.Text` bindings for computed total properties in `NouveauVoyageDialog.xaml`:

```xml
<!-- Before -->
<Run Text="{Binding VenteTotal, StringFormat='{}{0:N2} DH'}" />

<!-- After -->
<Run Text="{Binding VenteTotal, StringFormat='{}{0:N2} DH', Mode=OneWay}" />
```

## Bug 3 — ErrorMessage Visibility Binding Crash

### What happened
The error message panel in the dialog used an incorrect converter, causing a binding failure that prevented the dialog from rendering correctly.

### Root cause
The `ErrorMessage` visibility was bound with the wrong converter — it expected a `bool` value but `ErrorMessage` is a `string?`.

### Fix
Replaced the converter with `NullToVisibilityConverter` (already present in `Converters.cs`), which correctly returns `Visible` for non-null/non-empty strings and `Collapsed` otherwise.

## Bug 4 — PostgreSQL UTC DateTime Mismatch

### What happened
After the dialog opened and rendered correctly, submitting a voyage threw:

```
Cannot write DateTime with Kind=Unspecified to PostgreSQL type
'timestamp with time zone', only UTC is supported.
```

### Root cause
The `DateDepart` field in `NouveauVoyageViewModel` was initialized as a plain `DateTime` with `Kind=Unspecified`. Npgsql (the PostgreSQL driver) strictly rejects `Unspecified` kind values for `timestamp with time zone` columns — it requires `DateTimeKind.Utc`.

### Fix
- In `NouveauVoyageViewModel.cs`: normalized `DateDepart` on initialization and in the setter using `DateTime.SpecifyKind(value, DateTimeKind.Utc)`.
- In `VoyagesController.cs`: added a UTC normalization guard before saving, as a defensive backend layer:

```csharp
voyage.DateDepart = DateTime.SpecifyKind(dto.DateDepart, DateTimeKind.Utc);
```

## Bug 5 — Achat Numero varchar(20) Overflow

### What happened
All voyage sub-records (stock, ventes, crédits, frais) saved correctly, but every **Achat** failed with:

```
Microsoft.EntityFrameworkCore.DbUpdateException
Inner Exception: PostgresException: 22001: value too long for type character varying(20)
```

Error originated at `AchatsController.cs` line 49 (`SaveChangesAsync`).

### Root cause
The `Achat` model had `[StringLength(20)]` on the `Numero` field, which EF Core translated to a `character varying(20)` column in PostgreSQL. However, the number format generated by the client is:

```
A-yyyy-MM-dd-HH-mm-ss
```

For example: `A-2026-06-05-10-30-00` — which is **22 characters**, exceeding the 20-character limit. The insert was rejected at the database level.

Note: `Vente` and `Credit` already had `[StringLength(30)]` on their equivalent `Numero` fields — `Achat` was simply overlooked when the format was standardized.

### Fix
**Step 1** — Updated the model attribute in `FourniProApi/Models/Achat.cs`:

```csharp
// Before
[StringLength(20)]
public string? Numero { get; set; }

// After
[StringLength(30)]
public string? Numero { get; set; }
```

**Step 2** — Generated and applied an EF Core migration to update the live database column:

```bash
dotnet ef migrations add FixAchatNumeroLength
dotnet ef database update
```

This executed the following SQL on the PostgreSQL database:

```sql
ALTER TABLE "Achats" ALTER COLUMN "Numero" TYPE character varying(30);
```

## Lessons Learned

- **Always add a global `DispatcherUnhandledException` handler** in WPF apps during development — silent fatal crashes are extremely hard to diagnose without one.
- **`Run.Text` in WPF defaults to `TwoWay`** — always specify `Mode=OneWay` when binding to computed/read-only ViewModel properties inside `TextBlock`/`Paragraph` runs.
- **Npgsql strictly enforces `DateTimeKind.Utc`** for `timestamp with time zone` columns — never pass `Unspecified` kind values.
- **Keep `[StringLength]` attributes consistent** across all models that share the same auto-generated number format. A mismatch causes a runtime database error, not a compile-time one.
